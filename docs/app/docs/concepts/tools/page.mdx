# Tools

Tools give agents the power to *act*. Instead of only generating text, an agent with tools can read and write Frappe documents, call external APIs, run sub-agents, generate audio, and more.

---

## Agent Tool Function DocType

Every tool is defined as an **Agent Tool Function** record. This single DocType covers all tool types by swapping in the relevant fields based on the selected **Types** value.

### Core Fields

| Field | Fieldname | Type | Notes |
|---|---|---|---|
| Tool Name | `tool_name` | Data | Unique name. The agent sees exactly this string when choosing a tool. |
| Description | `description` | Small Text | Critical. The AI reads this to decide *when* to use the tool. Write in plain English. |
| Types | `types` | Select | Determines the underlying handler. See the table below. |
| Tool Type | `tool_type` | Link → Agent Tool Type | Category tag. Required. Used for UI grouping. |

### Tool Types Reference

| Type | What it does |
|---|---|
| `Get Document` | Fetches a single Frappe document by doctype + name |
| `Get Multiple Documents` | Fetches multiple documents by a list of names |
| `Get List` | Lists documents with optional filters, fields, and pagination |
| `Get Value` | Fetches the value of a single field from a document |
| `Set Value` | Sets the value of a single field on a document |
| `Create Document` | Creates a new Frappe document |
| `Create Multiple Documents` | Batch-creates documents from an array |
| `Update Document` | Updates fields on an existing document |
| `Update Multiple Documents` | Batch-updates multiple documents |
| `Delete Document` | Deletes a document (with permission check) |
| `Delete Multiple Documents` | Batch-deletes documents |
| `Submit Document` | Submits a submittable document |
| `Cancel Document` | Cancels a submitted document |
| `Get Amended Document` | Gets the amended copy of a cancelled document |
| `Attach File to Document` | Attaches a file URL to a document's attach field |
| `Get Report Result` | Runs a Frappe Report and returns results |
| `Custom Function` | Calls a Python function by dotted path |
| `App Provided` | Tool provided/registered by another installed app |
| `GET` | Makes an HTTP GET request to an external URL |
| `POST` | Makes an HTTP POST request to an external URL |
| `Run Agent` | Invokes another Huf agent as a sub-agent |
| `Speech to Text` | Transcribes audio to text |

## Type-Specific Fields

### DocType-Linked Tools

Most built-in tool types operate on a Frappe DocType:

| Field | Fieldname | Notes |
|---|---|---|
| Reference DocType | `reference_doctype` | The target DocType (e.g. `Sales Order`). Required for all DocType-operation types. |
| Parameters | `parameters` | Child table (`Agent Function Params`). Define what arguments the agent can pass. |
| Function Definition | `function_definition` | Read-only JSON. Auto-generated from parameters; sent to the LLM for tool calling. |

### Custom Function

| Field | Fieldname | Notes |
|---|---|---|
| Function Path | `function_path` | Dotted Python path (e.g. `myapp.api.process_order`). The function must accept keyword arguments matching the parameter definitions. |
| Pass Parameters as JSON | `pass_parameters_as_json` | If on, all parameters are bundled into a single `params` JSON string instead of individual kwargs. |

The referenced function should return a dict that the agent can interpret.

```python
# Example custom function
import frappe

def process_order(order_id: str, **kwargs):
    """Process a sales order and return updated status."""
    doc = frappe.get_doc("Sales Order", order_id)
    # ... processing logic ...
    return {
        "success": True,
        "order_id": doc.name,
        "status": doc.workflow_state
    }
```

### App Provided Tools

| Field | Fieldname | Notes |
|---|---|---|
| Provider App | `provider_app` | Name of the installed Frappe app that registers this tool. The app must call Huf's tool registration API during its setup. |

### HTTP Tools (GET / POST)

| Field | Fieldname | Notes |
|---|---|---|
| Base URL | `base_url` | Optional prefix applied before the URL argument. Allows agents to call relative paths (e.g. `/v1/products`) against a known base. |
| HTTP Headers | `http_headers` | Child table (`Agent Tool HTTP Header`) of `key` / `value` pairs. Injected into every request. Use for static auth tokens. |
| Allowed for Guest | `allowed_for_guest` | If checked, unauthenticated requests can use this tool via the HTTP handler. |

> [!CAUTION]
> Huf's HTTP handler (`http_handler.py`) performs **SSRF protection** before every request: it resolves the hostname's IP and blocks calls to private/internal address ranges (`10.x`, `172.16–31.x`, `192.168.x`, `127.x`, `::1`). This is enforced server-side and cannot be bypassed by the agent.

### Run Agent

| Field | Fieldname | Notes |
|---|---|---|
| Agent | `agent` | Link to the sub-agent to invoke. The calling agent passes a prompt to the sub-agent and receives its response as the tool result. |

## Parameters (Agent Function Params)

The `parameters` child table defines the JSON Schema that the LLM uses for tool calling. Each row is one parameter:

| Field | Notes |
|---|---|
| `param_name` | Parameter name (snake_case). |
| `type` | JSON Schema type: `string`, `number`, `integer`, `boolean`, `array`, `object`. |
| `description` | Explains this parameter to the agent. |
| `required` | If checked, the LLM must always supply this argument. |
| `default` | Optional default value if the agent omits the argument. |

When parameters are saved, Huf auto-generates the `function_definition` JSON (OpenAI function-calling format) that is sent to the LLM.

## Permission-Aware Execution

When an agent runs a tool, Huf's `PermissionAwareToolRegistry` checks Frappe's standard permission model **before executing**:

- For **mutating operations** (`Create`, `Update`, `Delete`, `Submit`, `Cancel`, `Set Value`, `Attach`): the current user must have write/delete/submit permission on the `reference_doctype`.
- For **read operations** (`Get`, `List`, `Get Value`): the current user must have read permission on the `reference_doctype`.

Mutating tools are defined in `MUTATING_TOOL_TYPES` in `tool_registry.py`. If the user lacks permission, the tool call is rejected with a permission error — the agent cannot bypass Frappe's access controls.

```python
# The check happens automatically:
frappe.has_permission(reference_doctype, ptype, raise_exception=True)
```

This means agents always operate with the permissions of the user who triggered them. Agents cannot escalate privileges.

## MCP Tools (Model Context Protocol)

In addition to native Huf tools, agents can connect to external **MCP Servers** to use their tools. MCP is an open protocol for LLM-tool interoperability.

Each MCP Server is registered as a separate **MCP Server** DocType record, then linked to agents via the `agent_mcp_server` child table.

### MCP Server Fields

| Field | Notes |
|---|---|
| `server_name` | Human-readable name |
| `server_url` | The MCP server's HTTP endpoint |
| `enabled` | Master enable/disable |
| `auth_type` | `bearer_token`, `api_key`, or `none` |
| `auth_header_name` / `auth_header_value` | Auth header key-value pair |
| `tool_namespace` | Optional prefix applied to all tools from this server (e.g. `github.create_issue`) |
| `timeout_seconds` | Per-request timeout. Default: 30s. |
| `enable_auto_sync` | Auto-refreshes the tool list on a schedule |
| `auto_sync_interval` | Hours between auto-syncs |

### Syncing Tools

Click **Sync Tools** on the MCP Server record to fetch and cache available tools. Huf communicates with the MCP server using JSON-RPC 2.0 (`tools/list` and `tools/call` methods). The tool list is stored in the `tools` child table, where you can enable/disable individual tools.

### Enabling MCP on an Agent

1. Open the Agent.
2. In **Agent MCP Server** (child table), add a row and select the MCP Server.
3. Check **Enabled**.
4. Save.

MCP tools are presented to the LLM alongside native Huf tools with a `[MCP: server_name]` prefix in the description.

## Tool Sync

The **Agent Tool Sync** mechanism (via `PermissionAwareToolRegistry.sync_tools`) keeps the agent's tool list in sync with its `agent_tool` child table. It filters out tools that the current user doesn't have permission to use based on the underlying DocType permissions.

## Creating a Custom Tool — Step by Step

1. **Navigate** to **Huf → Agent Tool Functions → New**.
2. Set **Tool Name** (e.g. `send_whatsapp_message`).
3. Set **Types** to `Custom Function`.
4. Write a **Description** that explains *when* the agent should use this tool.
5. Set **Function Path** to the Python function (e.g. `myapp.whatsapp.send_message`).
6. Add **Parameters** (e.g. `recipient_phone: string`, `message: string`).
7. Save. The **Function Definition** JSON is auto-generated.
8. Open an **Agent**, go to **Agent Tool** tab, and add this tool.

The agent can now call `send_whatsapp_message` when it needs to send a message.

## Best Practices

- **Keep descriptions specific** — vague descriptions lead to the agent calling the wrong tool.
- **Minimise required parameters** — the more required fields, the harder it is for the agent to call the tool correctly.
- **Return structured data** — have custom functions return a dict with `success`, `data`, and optional `error` fields.
- **One tool, one responsibility** — avoid multi-purpose tools; they confuse the agent's decision making.
- **Test in Agent Console** — use the Agent Console to test tool calls before deploying.
