# المحفّزات

تحدد المحفّزات **متى** و**كيف** تعمل الوكلاء تلقائيًا. بدلًا من تشغيل الوكلاء يدويًا، تتيح لهم المحفّزات الاستجابة للأحداث، أو العمل وفق جداول زمنية، أو التنفيذ بناءً على شروط محددة.

## ما هي المحفّزات؟

المحفّز هو قاعدة تنفيذ آلية للوكيل. باستخدام المحفّزات، يمكن للوكيل أن يعمل وفق جدول زمني مثل كل ساعة أو يوميًا، أو أن يتفاعل مع أحداث دورة حياة المستندات مثل الإنشاء أو الإرسال، أو أن يُرشّح عمليات التنفيذ من خلال شروط، وأن يحافظ على سجلات محادثات منفصلة لكل مستخدم. هذه القدرات تحوّل الوكلاء من أدوات عند الطلب إلى **أتمتة استباقية**.

## أنواع المحفّزات

تنقسم المحفّزات إلى خمس فئات واسعة حسب من أو ما الذي يبدأها وسواء كانت تعمل داخل المنتج أو من نظام خارجي.

### 1. التنفيذ اليدوي

يوفّر التنفيذ اليدوي تحكمًا مباشرًا لك: تشغّل الوكيل بالضبط عند الحاجة، دون أي إعداد للمحفّز. يمكنك بدءه من خلال **Agent Chat** في الوقت الفعلي، أو النقر على **Run** في نموذج **Agent DocType**، أو استدعاء طريقة `run_agent_sync` من الكود الخاص بك. هذا الخيار الأفضل لاختبار الوكيل، ومعالجة المهام لمرة واحدة، ودعم التفاعلات التي يبدأها المستخدم، وتصحيح السلوك.

<Callout type="info">لا يحتاج التنفيذ اليدوي إلى إعداد محفّز—فقط شغّل الوكيل عندما تريد.</Callout>

### 2. المحفّزات المجدولة

تجعل المحفّزات المجدولة الوكيل يعمل بشكل متكرر بفواصل زمنية ثابتة. وهي مفيدة عندما يحتاج الوكيل إلى إخراج متكرر دون أن يتذكر أحد أن يبدأه، مثل التقارير اليومية أو الفحوصات الدورية للصحة. يتم إعدادها من خلال DocType **Agent Trigger**.

| التكرار | الوصف |
|---|---|
| **Hourly** | يعمل كل ساعة |
| **Daily** | يعمل مرة واحدة يوميًا في وقت محدد |
| **Weekly** | يعمل في أيام محددة من الأسبوع |
| **Custom Cron** | جدولة متقدمة باستخدام تعبير cron |

تتضمن حالات الاستخدام الشائعة إنشاء التقارير اليومية، وفحص المخزون كل ساعة، ومهام التلخيص الأسبوعية، ومزامنة البيانات الدورية، والإشعارات المجدولة.

**مثال:**

<ConfigPanel title="مثال محفّز">
  <ConfigField label="Agent" value="ملخص المبيعات اليومي" />
  <ConfigField label="Trigger" value="كل يوم في الساعة 9:00 صباحًا" />
  <ConfigField label="Action" value="يُنشئ تقرير المبيعات ويرسله عبر البريد الإلكتروني" />
</ConfigPanel>

### 3. محفّزات أحداث المستندات

تستجيب محفّزات أحداث المستندات للتغييرات في مستندات Frappe، بحيث يمكن للوكلاء التحقق من صحة السجلات أو توجيهها أو إثرائها أثناء مرورها بسير العمل. يتيح ذلك للأتمتة أن تبقى مرتبطة بشكل وثيق ببيانات الأعمال التي تتصرف بناءً عليها.

| الحدث | الوصف |
|---|---|
| **After Insert** | تم إنشاء المستند |
| **On Update** | تم تعديل المستند |
| **On Submit** | تم إرسال مستند قابل للإرسال |
| **On Cancel** | تم إلغاء المستند |
| **Before Save** | قبل حفظ المستند (استخدم بحذر) |
| **After Delete** | تم حذف المستند (استخدم نادرًا) |

تتضمن حالات الاستخدام النموذجية التحقق من الفواتير عند الإرسال، وتعيين العملاء المحتملين تلقائيًا عند إنشائهم، وإخطار الفريق عند تحديث الصفقات، وتشغيل فحوصات الجودة عند إرسال المستند، وإثراء البيانات عند الإنشاء.

**مثال:**

<ConfigPanel title="مثال محفّز">
  <ConfigField label="Agent" value="مدقق الفواتير" />
  <ConfigField label="Trigger" value='After Submit على DocType "Sales Invoice"' />
  <ConfigField label="Action" value="يتحقق من التسعير، وفحص حدود الائتمان، ويُعلّم على المشكلات" />
</ConfigPanel>

### 4. التنفيذ عبر الدردشة

يتيح التنفيذ عبر الدردشة للمستخدمين التحدث إلى الوكيل من خلال واجهة دردشة. لتفعيله، اضبط `allow_chat = 1` على **Agent DocType**. يمكن بعد ذلك الوصول إلى الوكيل من **Agent Chat** DocType في Desk ومن واجهة `/huf` الأمامية، والتي تتوسّع حاليًا. هذا الوضع مفيد لدعم العملاء، والمساعدات التفاعلية، وسير العمل المحادثي، وأي وكيل موجّه للمستخدم.

<Callout type="info">لا يتطلب التنفيذ عبر الدردشة محفّزًا منفصلاً—يتم تمكين الدردشة على الوكيل نفسه.</Callout>

### 5. التنفيذ عبر واجهة API

يتيح التنفيذ عبر API للأنظمة الخارجية استدعاء الوكيل عبر HTTP. يعرض الوكيل طريقة `run_agent_sync` المدرجة في القائمة البيضاء، وتستخدم الطلبات مصادقة API القياسية في Frappe. هذا هو الخيار المناسب لتكاملات webhook، وأتمتة التطبيقات الخارجية، والواجهات الأمامية المخصصة، وتكامل خدمات الطرف الثالث.

**نقطة النهاية:** `run_agent_sync` (طريقة مدرجة في القائمة البيضاء)

**المصادقة:** مصادقة API القياسية في Frappe

**مثال:**
```python
response = requests.post(
    "https://yoursite.com/api/method/huf.ai.agent_integration.run_agent_sync",
    headers={"Authorization": f"token {api_key}:{api_secret}"},
    json={
        "agent_name": "Customer Support Agent",
        "prompt": "What is the status of order SO-001?",
        "session_id": "api:external_system:12345"
    }
)
```

## Agent Trigger DocType

يتم إعداد المحفّزات المجدولة وأحداث المستندات معًا من خلال DocType **Agent Trigger**. لإنشائها أو إدارتها، انتقل إلى **Desk → Huf → Agent Trigger**.

### الحقول الرئيسية

يحتوي نموذج Agent Trigger على الحقول التي تحدد أي وكيل يعمل، ومتى يعمل، والتعليمات التي يتلقاها.

| الحقل | الوصف |
|-------|-------------|
| **Agent** | أي وكيل سيعمل |
| **Trigger Type** | جدولة أو حدث مستند |
| **Reference DocType** | لأحداث المستندات، أي DocType |
| **Document Event** | أي حدث (After Insert، On Submit، إلخ) |
| **Condition** | شروط التصفية الاختيارية |
| **Schedule** | للمحفّزات المجدولة، التكرار/الوقت |
| **Prompt Template** | الرسالة المرسلة إلى الوكيل |
| **Enabled** | مفتاح التفعيل/التعطيل |

### إنشاء محفّز

لإعداد محفّز جديد، افتح **Agent Trigger** وانقر **New**، ثم املأ النموذج واحفظه. العملية هي:

## إعداد المحفّز المجدول

تحتاج المحفّزات المجدولة إلى تكرار أو تعبير cron وموجه (prompt) يخبر الوكيل بما يجب فعله في كل مرة يعمل فيها.

### ضبط الجدول

تعتمد المحفّزات المجدولة على تكرار أو تعبير cron لتحديد وقت استيقاظ الوكيل. اختر الخيار الذي يتناسب مع عدد مرات تشغيل المهمة.

| خيار التكرار | وقت التشغيل |
|---|---|
| **Hourly** | يعمل كل ساعة |
| **Daily** | حدد وقتًا مثل `"09:00"` |
| **Weekly** | اختر أيامًا ووقتًا |
| **Cron** | جدولة متقدمة بتعبير cron |

**أمثلة:**
```
Daily at 9 AM: "0 9 * * *"
Every Monday at 2 PM: "0 14 * * 1"
Every 30 minutes: "*/30 * * * *"
First day of month: "0 0 1 * *"
```

### قوالب الموجهات للمحفّزات المجدولة

يخبر قالب الموجه الوكيل المجدول بما يجب فعله في كل مرة يعمل فيها. يمكنك إبقائه ثابتًا أو تضمين تعليمات ديناميكية حول اليوم الحالي أو الفترة أو مجموعة البيانات.

```
Generate a summary of today's sales and send it to the sales team.
```

أو مع بيانات ديناميكية:

```
Check inventory levels and alert if any items are below reorder point. 
Focus on fast-moving items from the last 7 days.
```

**مثال محفّز:**

<ConfigPanel title="مثال محفّز">
  <ConfigField label="Agent" value="مراقب المخزون" />
  <ConfigField label="Schedule" value="كل يوم في الساعة 8:00 صباحًا" />
</ConfigPanel>

**الموجه:**
```
"Check inventory for items below reorder level and create purchase
requisitions if needed. Prioritize high-demand items."
```

## إعداد محفّز أحداث المستندات

تحتاج محفّزات أحداث المستندات إلى DocType وحدث وشروط اختيارية وموجه يمكنه الإشارة إلى حقول المستند.

### اختيار الـ DocType

أولاً، اختر DocType الذي يجب أن يراقبه المحفّز. حقل **Reference DocType** هو اسم نوع المستند، مثل `"Sales Invoice"` أو `"Lead"` أو `"Support Ticket"`.

### اختيار الحدث

بعد ذلك، اختر حدث المستند الذي يبدأ الوكيل. يُطلق كل حدث في نقطة مختلفة من دورة حياة المستند.

| الحدث | وقت الإطلاق |
|-------|---------------|
| **After Insert** | بعد إنشاء المستند وحفظه |
| **On Update** | عند تعديل المستند |
| **On Submit** | عند إرسال مستند قابل للإرسال |
| **On Cancel** | عند إلغاء المستند |
| **Before Save** | قبل الحفظ (يمكن منع الحفظ بأخطاء) |
| **After Delete** | بعد حذف المستند |

<Callout type="info">الأحداث الأكثر استخدامًا هي **After Insert** و**On Submit** و**On Update**.</Callout>

### التنفيذ الشرطي

تتيح لك الشروط تشغيل محفّز حدث المستند فقط عندما يطابق المستند قيم حقول محددة، مما يمنع تشغيل الوكيل بلا داعٍ ويحافظ على التكاليف المتوقعة. يقبل حقل **Condition** كائن JSON للتصفية.

**أمثلة على الشروط:**
```json
{
  "status": "Open",
  "priority": "High"
}
```
→ يُشغّل فقط إذا كانت حالة المستند "Open" والأولوية "High"

```json
{
  "grand_total": [">", 10000]
}
```
→ يُشغّل فقط إذا تجاوز grand_total 10,000

```json
{
  "customer_group": ["in", ["Wholesale", "Distributor"]]
}
```
→ يُشغّل فقط لمجموعات عملاء محددة

<Callout type="warning">إذا تركت الشرط فارغًا، فإن المحفّز يُطلق عند كل حدث مطابق لهذا DocType.</Callout>

### قوالب الموجهات لمحفّزات أحداث المستندات

بالنسبة لمحفّزات المستندات، يمكن أن يتضمن قالب الموجه عناصر نائبة مثل `{field_name}` لإدراج قيم من المستند الحالي.

```
A new lead has been created: {lead_name} from {company_name}.
Please review the lead, score it based on our criteria, and assign 
it to the appropriate sales rep.

Lead Details:
- Email: {email_id}
- Source: {source}
- Territory: {territory}
```

تتضمن البيانات المتاحة للموجه جميع الحقول الموجودة في المستند، والحقول القياسية مثل `name` و`creation` و`modified` و`owner`، وبيانات المستندات المرتبطة عندما يملك الوكيل أدوات يمكنها جلبها.

**مثال:**

<ConfigPanel title="مثال محفّز">
  <ConfigField label="Agent" value="مؤهل العملاء المحتملين" />
  <ConfigField label="DocType" value="Lead" />
  <ConfigField label="Event" value="After Insert" />
</ConfigPanel>

**الموجه:**
```
"A new lead was created: {lead_name} from {company_name}
in {territory}. Score this lead, assign to appropriate sales
rep, and set next follow-up date."
```

## أوضاع المحادثة للمحفّزات

يمكن للمحفّزات استخدام سجل محادثات لكل مستخدم أو سجل مشترك، حسب رغبتك في عزل المستخدمين أو الاستمرارية بين عمليات التشغيل.

### محادثة لكل مستخدم

افتراضيًا، تحافظ المحفّزات على سجل كل مستخدم بشكل منفصل (`persist_user_history = 1`). يحافظ هذا على الخصوصية ويضمن عدم تسرّب السياق الخاص بالمستخدم بين المستخدمين. على سبيل المثال، إذا عمل وكيل تذكرة الدعم عند الإرسال، يُنشئ إرسال المستخدم A محادثة منفصلة للمستخدم A، ويُنشئ إرسال المستخدم B محادثة منفصلة للمستخدم B، وتظل السجلات مستقلة.

### المحادثة المشتركة

في الوضع المشترك (`persist_user_history = 0`)، تشترك جميع عمليات تنفيذ المحفّز في محادثة واحدة. يتيح هذا للوكيل بناء معرفة تراكمية: يمكن لوكيل ملخص المبيعات اليومي المجدول أن يتذكر تقرير الأمس، ومقارنة الاتجاهات، والبناء على بيانات الأيام السابقة. يمكنك إعداد ذلك على **Agent DocType** باستخدام مفتاح **Persist Conversation** ومربع الاختيار **Persist per User (Doc/Schedule)**: حدده لسجل لكل مستخدم، أو ألغ تحديده لسجل مشترك.

### معالجة الأخطاء

تعمل محفّزات الوكيل دون مراقبة، لذا فإن المراقبة ضرورية. تحقق بانتظام من سجلات Agent Run، وقم بإعداد إشعارات الفشل، وراجع الأخطاء وعدّل الموجهات، واختبر شروط المحفّز بدقة.

## حالات الاستخدام الشائعة

تُظهر هذه الأمثلة كيف تجمع المحفّزات بين أنواع الأحداث والوكلاء وقوالب الموجهات لأتمتة سير العمل الشائعة.

### 1. التعيين التلقائي للعملاء المحتملين

عند إنشاء Lead جديد، يمكن لوكيل Lead Router تقييم المنطقة وحجم العمل والملاءمة الصناعية لتعيين أفضل مندوب مبيعات وتحديد موعد المتابعة التالية.

<ConfigPanel title="مثال محفّز">
  <ConfigField label="Trigger" value="After Insert على Lead" />
  <ConfigField label="Agent" value="Lead Router" />
</ConfigPanel>

**الموجه:**
```
New lead: {lead_name} from {territory}.
Assign to the best sales rep based on:
- Territory coverage
- Current workload
- Specialization in {industry}
Update the lead with assigned rep and next follow-up date.
```

### 2. التحقق من الفواتير

عند إرسال Sales Invoice، يمكن لوكيل Invoice Validator التحقق من التسعير وحدود الائتمان والضرائب والشذوذ قبل إنهاء الفاتورة.

<ConfigPanel title="مثال محفّز">
  <ConfigField label="Trigger" value="On Submit على Sales Invoice" />
  <ConfigField label="Agent" value="Invoice Validator" />
</ConfigPanel>

**الموجه:**
```
Validate this invoice:
- Check pricing against price list
- Verify credit limit for customer {customer}
- Confirm tax calculations
- Flag any anomalies
If issues found, add comment and notify accounts team.
```

### 3. إنشاء التقارير اليومية

يمكن للتشغيل الصباحي المجدول إنتاج ملخص مبيعات يومي وإرساله إلى الفريق دون تدخل يدوي.

<ConfigPanel title="مثال محفّز">
  <ConfigField label="Trigger" value="Schedule (Daily at 9 AM)" />
  <ConfigField label="Agent" value="Sales Report Generator" />
</ConfigPanel>

**الموجه:**
```
Generate daily sales summary:
- Total orders and revenue
- Top 5 customers
- Pending payments
- Trends vs yesterday
Send report to sales@company.com
```

### 4. توجيه تذاكر الدعم

عند وصول Support Ticket جديدة، يمكن لوكيل Ticket Router فرز الأولوية وتحديد SLAs وتوجيه التذكرة إلى الفريق المناسب.

<ConfigPanel title="مثال محفّز">
  <ConfigField label="Trigger" value="After Insert على Support Ticket" />

## استكشاف الأخطاء وإصلاحها

عندما لا يتصرف المحفّز كما هو متوقع، استخدم الأعراض أدناه لتحديد السبب.

**المحفّز لا يعمل:**
- تأكد من أن المحفّز **Enabled**.
- تحقق من أن الشرط يطابق المستند.
- راجع اختيار DocType والحدث.
- تأكد من أن الوكيل نشط.
- تحقق من عدم وجود مشاكل أذونات في Frappe.

**المحفّز يعمل بكثرة:**
- أضف شروطًا أكثر تحديدًا.
- غيّر من "On Update" إلى "On Submit".
- راجع سير عمل المستند.
- تحقق من وجود حلقات محفّزات.

**الوكيل يحصل على بيانات خاطئة:**
- تحقق من أسماء حقول قالب الموجه.
- تحقق من حالة المستند عند تشغيل المحفّز.
- اختبر الوصول إلى الحقول والأذونات.
- راجع أدوات الوكيل المخصصة.

**تكاليف مرتفعة من المحفّزات:**
- قلل تكرار المحفّز.
- أضف شروطًا أكثر صرامة.
- استخدم نماذج أرخص للمحفّزات البسيطة.
- حد من طول سجل المحادثة.

**مشاكل الأداء:**
- وزّع المحفّزات المجدولة.
- استخدم مهام الخلفية للمهام الثقيلة.
- حسّن أدوات الوكيل.
- راجع مدة Agent Run.
